# Security policy

## Supported versions

pachifast is in alpha. Only the latest released minor version receives security fixes.

| Version | Supported |
| --- | --- |
| latest minor (0.15.x) | yes |
| older versions | no: upgrade, see [Upgrading](docs/guides/upgrading.md) |

## Reporting a vulnerability

Do **not** open a public issue for a security problem. Write to the maintainer (ilPachi) at
**ilpachi@ilpachi.it** with the subject "pachifast security". Include the affected version, a description of the
impact and, if possible, steps to reproduce.

You can expect an acknowledgement within a few days. Disclosure is coordinated: please give us up to **90 days** from your report to release a fix before you publish details; we will tell you sooner when it is ready, and agree a date with you if a fix needs longer. A fix is released as a patch version and noted in the
[changelog](CHANGELOG.md); reporters are credited unless they prefer otherwise.

## Scope

In scope: authentication, tokens, MFA, permissions, the admin routes, the events (WebSocket) layer, migrations and
the files generated by the CLI. The authentication code is self-assessed against OWASP ASVS level 1 and has not
been independently audited: review it before using it for sensitive data.

## Known limitations

- The TOTP secrets are encrypted at rest (Fernet), but the key is in the configuration: whoever can read both the database and `SECRET_KEY` / `MFA_ENCRYPTION_KEY` can generate the codes. The backup codes and the one-time codes are hashed. Keep the key out of backups of the database.
- The routes of login, registration and the second-factor check have no limit per client address unless `auth_rate_limit` is set; the lockout of an account (`login_max_attempts`) can be used to keep a known username locked.
- Username enumeration: when registration is open, the answer to a taken username tells that it exists.
